   44| ### 3. AI-specific concerns
   45| 
   46| - **Over-trust / automation bias:** Stanford (Perry et al., CCS 2023) as above: AI-assisted participants wrote less secure code and were more confident it was secure. Automation-complacency research (Parasuraman) shows detection of automation failures can fall dramatically when a system is usually reliable.
   47| - **Vigilance decrement:** A robust attention finding — monitoring performance drops after the first ~30 minutes. Stacked with automation bias and context-switching, this produces "review fatigue": deep evaluation degrades to surface scanning.
   48| - **Code-quality erosion:** GitClear (211M LOC): moved/refactored code fell from 24.8% (2021) to 9.5% (2024) while copy/paste rose from 8.4% to 12.3%; duplicate blocks up eightfold in 2024; churn roughly doubling. AI code is codebase-unaware and redundancy-prone.
   49| - **Security:** "Asleep at the Keyboard?" (Pearce et al., IEEE S&P 2022): from 89 scenarios producing 1,689 programs, "we found approximately 40% to be vulnerable" (39.33% of top suggestions) across CWE Top-25 scenarios.
   50| - **Hallucinated APIs / slopsquatting:** LLMs invent plausible non-existent package names; attackers register them. Lasso Security's Bar Lanyado uploaded an empty PyPI package under the LLM-hallucinated name "huggingface-cli" (the real install is `pip install -U "huggingface_hub[cli]"`), and it "received over 30,000 downloads in three months" — even Alibaba copy-pasted the fake install command into a public repo README. Spracklen et al., "We Have a Package for You!" (USENIX Security 2025), tested 16 LLMs across 576,000 samples and found "19.7% of the generated packages are fictitious"; commercial models hallucinated at 5.2% versus 21.7% for open-source models (GPT-4 Turbo lowest at 3.59%). A 2026 re-evaluation ("The Range Shrinks, the Threat Remains") found newer frontier models still hallucinate at ~4.6%–6.1% per model, with 127 package names invented identically by five different models — so validation remains necessary.
   51| - **What changes for the reviewer:** Human code errors cluster around author intent (typos, off-by-one, forgotten cases). AI errors are *plausible-but-wrong*: confident code that compiles and reads cleanly but hallucinates APIs, misses edge cases, duplicates existing logic, or silently mis-implements the spec. So the reviewer must shift attention from "is this well-written?" to "does this do what was intended, and does the API/package actually exist and integrate?"
   52| 
   53| ### 4. The main event — techniques that re-state or re-present AI output (prioritized)
   54| 
   55| **Tier A — highest comprehension-per-effort**
   56| 
   57| 1. **Review the plan/spec before the code (intent–implementation separation).** Have the AI produce a structured spec (what/why/constraints) and a step-by-step plan, and review *those* before any code exists. Spec-driven development (GitHub Spec Kit's `/specify` → `/plan` → `/tasks`; Cursor/Copilot "plan mode"; Kiro's spec-driven flow) makes the spec the reviewable source of truth. Cognitive basis: reviewing a one-page plan is a fraction of the intrinsic load of reviewing 500 LOC, and approving intent first lets you review the code top-down against confirmed hypotheses. Every step should be steerable (edit spec → edit plan → edit code).
   58| 
   59| 2. **Make the AI explain itself, including a "least-confident" section.** Require every AI output to ship with: a plain-English summary of what it does, the assumptions it made, design decisions and alternatives rejected, explicit risk callouts, and a "what I am least confident about / what I did not test" section. This is the AI analogue of the Cisco author-annotation finding, and it directs the reviewer's scarce attention to the highest-risk spots. Example prompt: *"Before showing code, list your assumptions, the edge cases you did and did not handle, any APIs/packages you are not certain exist, and the three things most likely to be wrong."*
   60| 
   61| 3. **Read the tests as a restatement of behavior.** Reviewing tests (and property-based tests / executable specifications) is often faster and higher-signal than reviewing implementation, because tests state intended behavior in enumerable cases. Property-based testing (the QuickCheck lineage; used in industrial practice at companies including Amazon, Volvo, and Stripe) is an "executable specification" — you review the *properties* (universal invariants) rather than every line. Guard against the trap of the AI writing tests that merely ratify its own buggy code: have an independent agent or human derive tests from the spec, isolated from the implementer (Google SRE guidance: "the AI agent that generates the source code must be strictly isolated from the AI agent that defines the test cases or reviews the output... This separation prevents the transmission of cross-bias").
   62| 
   63| **Tier B — high value, modest effort**
   64| 
   65| 4. **Chunk into reviewable units and tier by risk.** Split large AI outputs by system boundary (API vs DB vs UI), separate refactors from new features, and keep each reviewable chunk near the ~200 LOC sweet spot. Then apply *tiered review*: line-by-line scrutiny for security-critical / irreversible / high-blast-radius code; spot-check sampling for low-risk boilerplate. This directly respects the 200–400 LOC and 60–90 minute limits.
   66| 
   67| 5. **Multi-level / layered summaries (progressive disclosure).** Present output as executive summary → architecture → module → line, so the reviewer builds a schema top-down and drills only where needed. LLM-generated "natural-language outlines" (interleaved NL statements that partition code into summarized logical sections) and multi-level (function/file/project) summaries operationalize this. Cognitive basis: progressive disclosure keeps working memory within capacity at each level.
   68| 
   69| 6. **Dual-coded visualization.** Auto-generate control-flow, data-flow, dependency, and architecture diagrams (e.g., Mermaid) alongside the text. Pair each diagram with a one-line caption. Reserve for genuinely complex flows; skip for trivial code to avoid added load.
   70| 
   71| **Tier C — powerful for high-stakes or ambiguous code**
   72| 
   73| 7. **Natural-language back-translation + comparison.** Ask a *different* model (or a fresh session) to describe what the code actually does, then compare that description to the original intent/spec. Divergence localizes bugs. Mutation-style consistency checking (does the summary change when the behavior changes?) is the research backbone here.
   74| 
   75| 8. **Adversarial / cross-examination second model.** Use a second model tasked to *attack* the output: "find the three most likely bugs, the missing edge cases, and any hallucinated APIs." This counteracts the sycophancy and single-model blind spots that make reviewers feel good about bad AI code (the "reviewer's blind spot"). Keep the human reviewer as final judge.
   76| 
   77| 9. **Prompt for review-friendly output up front.** The cheapest re-presentation is generating comprehensible output in the first place: request small, single-purpose diffs; inline rationale comments at non-obvious points; explicit flagging of any new dependency; and a self-generated checklist of what the reviewer should verify.
   78| 
   79| ### 5. Practical workflows (2025–2026)
   80| 
   81| - **Trust but verify; oversight moves "up the abstraction ladder."** Google SRE guidance ("AI in SRE") is explicit that "Traditional line-by-line code review does not scale with a 4x to 10x increase in code volume. Attempting to maintain this practice leads to reviewer fatigue and rubber-stamping. Instead, human oversight must 'shift left' and move up the abstraction ladder. Engineers must focus on reviewing Designs, Intent, and Policies." Google Cloud's Office of the CTO similarly warns of "approval fatigue," where developers "start clicking 'Approve' reflexively."
   82| - **Anthropic / Claude Code:** read-only by default, approval required before modifying code/systems, real-time steering, and the single most-emphasized practice is **verification — give the agent a way to check its own output**. Anthropic's own usage data shows experienced users shift from approving each action toward monitoring and intervening; they caution *against* mandating approval of every action as "friction without necessarily producing safety benefits." Recommended safeguards: minimum permissions, reversible actions, clear stopping conditions, and human checkpoints for high-stakes decisions.
   83| - **GitHub (agentic PRs):** agent PRs are created for human review and not auto-merged; treat an agent run as a production change request with a run record (task, repo/ref, permissions, model), separate read-only exploration from state-changing actions, and make dependency changes a distinct approval gate.
   84| - **Empirical reality check:** The EASE 2026 study "These Aren't the Reviews You're Looking For" (Duma, Wróblewski, Bobińska, Winiarska & Przymus, Nicolaus Copernicus University), mining the AIDev dataset (>932k PRs, repos with ≥100 stars), found that of all human comments on AI-authored PRs, 64.53% were "direct human review" (evaluative plus workflow feedback, which annotators could not reliably separate), 28.37% were agent-steering interactions, and 7.10% were CI/automation messages; 71.58% of all review comments on AI PRs were authored by agents rather than humans. Crucially, on human-authored PRs 93.56% of human comments were direct review with steering nearly absent (1.63%), versus 65.53% direct review and 25.92% steering on AI-authored PRs — the review *effort is structured differently*, with far fewer human-only reviews of AI PRs (8.08% vs 25.21%). Review depth is light across the board (reviewed PRs average 2–3 comments). Combined with the "More Code, Less Reuse" sentiment finding, the message is: observable review activity is a poor proxy for real oversight. Design the workflow to force active engagement (friction roles: state your expected behavior before seeing the AI's output; require reconciliation on divergence).
   85| - **Named accountability:** An AI is not an author and cannot hold accountability; name one human of record per PR.
