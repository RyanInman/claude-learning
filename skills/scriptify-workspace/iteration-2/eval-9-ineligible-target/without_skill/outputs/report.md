## Blocker: target is ineligible for writes

The skill lives under `plugins/cache/`. That directory is a **plugin cache** - content managed and regenerated by the plugin system from the upstream `release-tools` plugin, not a source tree.

Writing there is unsafe: the next plugin update (install, refresh, version bump, or cache eviction) re-materializes the directory from upstream and **overwrites or deletes anything written into it**. Generated scripts and a rewritten `SKILL.md` would vanish without warning, and any run in between would silently drift back to the un-scriptified behavior. Cache paths are also not tracked by the project's VCS, so the work would be unreviewable and unrecoverable.

**Nothing was written or modified under the cache path.** The classification below was produced read-only. Baseline file hashes were captured before analysis and re-verified after; the tree is byte-identical to its baseline (see `transcript-notes.md`).

## Per-step classification

| # | Step (SKILL.md) | Class | Reasoning |
|---|---|---|---|
| 1 | List every `.md` file in `notes/`, sorted by filename, note total count | **Script** | Pure filesystem enumeration + sort + count. Fully deterministic, no judgment. Re-deriving it in prose costs tokens and invites miscounts or missed files on every run. |
| 2 | Check each file starts with `PR #<number>:`; record failures | **Script** | Fixed regex validation (`^PR #\d+:`) over a known file set. Binary pass/fail per file. A model re-reading the rule each run is the classic source of run-to-run variance - e.g. `pr-104.md` starts `Merged 104:` and must be flagged every single time. |
| 3 | Group entries by `type:` field (`feat`, `fix`, `chore`) and count each group | **Script** | Field extraction, bucketing, tallying against a closed vocabulary. Deterministic aggregation; also lets unknown or missing `type:` values be reported explicitly rather than silently guessed. |
| 4 | Write a two-sentence summary of the release for the customer-facing changelog | **Claude** | Requires reading intent behind the changes, judging what matters to a customer, and producing natural prose within a length constraint. No deterministic rule produces this. This is the one step where the model is specifically needed. |
| 5 | Render final notes as a markdown list, grouped by type, sorted by PR number ascending | **Script** | Pure formatting from structured data already computed in steps 1-3. Sorting is numeric on the parsed PR number; grouping order is fixed. Rendering in prose is the highest-variance, lowest-value use of model tokens in the skill. |

Summary: 4 of 5 steps are script-eligible; 1 step (the summary paragraph) stays with Claude.

### Delegations that would be applied

Had the target been eligible, the apply stage would add:

- `scripts/collect_notes.py` - covers steps 1-3. Enumerates `notes/*.md` sorted by filename, validates the `PR #<number>:` header, parses `type:`, emits JSON: `{total, entries:[{file, pr, title, type}], invalid:[file...], counts:{feat, fix, chore}}`.
- `scripts/render_notes.py` - covers step 5. Consumes that JSON plus the step-4 summary text and prints the final grouped, PR-ascending markdown.

`SKILL.md` steps 1-3 and 5 would be rewritten to invoke those two scripts and interpret their output; step 4 would remain prose instruction. Both scripts would then be smoke-tested against the three fixture notes, whose expected result is: total 3, one invalid file (`pr-104.md`), counts `feat 1 / fix 1 / chore 1`, with `pr-104` flagged rather than silently dropped.

None of the above was written. See `gate.md`.
